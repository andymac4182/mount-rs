  outside the supported N-API inspection surface; their behavior is qualified
  through wire operations, effective knobs, lease sweeping, shared handles,
  and live callback tests.
- Exercise the full v3/v4 behavior matrix, including stateful v4 operations,
  malformed records, reconnects, and version negotiation. The shared router
  now returns `RPC_PROG_MISMATCH` with the advertised NFSv3..v4 range for
  unsupported NFS versions, while MOUNT remains v3-only; a real-TCP test
  covers both directions, valid versions, unknown programs, wrong RPC version,
  and unsupported auth. The direct N-API path uses the same router, and its
  unsupported-version runtime assertion passes with the loadable local addon.
- The rootless wire suite now drives two independent NFSv4.1 sessions through
  concurrent distinct-file OPEN/WRITE/READ round trips. This closes a bounded
  in-process multi-client userspace case. Multiple server processes sharing a
  backend are explicitly outside supported scope because session, lease,
  replay, and handle arbitration is process-local; native-client ordering
  remains a separate hosted/platform gate.
- A rootless NFSv4.1 retry now proves a cached, mutating `REMOVE` reply survives
  an orderly TCP disconnect/reconnect while the server process remains alive.
  Reusing the same slot/sequence with a changed target returns the original
  body without executing the changed operation; a fresh sequence still makes
  progress. A separate blocked-backend test proves an in-flight same-slot
  retry reaches the server, waits, and then receives the cached original
  reply. An early active-slot check now returns prompt `NFS4ERR_DELAY` for the
  in-flight retry and `NFS4ERR_SEQ_MISORDERED` for a premature next sequence;
  the completed request still caches its reply, and slot sequence numbers
  wrap to zero. A second blocked-backend test now proves that slot 1 of the
  same session completes over another TCP connection while slot 0 remains
  blocked. The handler checks for expired leases under the shared read lock
  and takes the exclusive path lock only when a sweep is needed. A separate
  injected-clock test proves that, once the lease expires during a blocked
  slot-0 request, slot 1 waits for the sweep and then gets `NFS4ERR_BADSESSION`;
  the existing expired-session wire test also still passes. This is bounded
  same-process overlap, not crash-durable replay or native-client ordering.
- A mutating v4.1 COMPOUND canceled before completion and reply-cache commit
  now fails closed: the accepted slot's session is invalidated, so a retry
  cannot re-execute an operation with uncertain effects. A real-TCP test removes a
  file in the backend, stops that connection before the reply exists, gets
  `NFS4ERR_BADSESSION` when retrying with a changed target, and uses a new
  session for the same client to make progress. `CREATE_SESSION` now echoes a
  noninitial request sequence in its reply. This is session-fenced recovery,
  not preservation of the canceled operation's exact reply or its prior
  session; other cache-required oversized replies, native-client ordering, and
  crash-durable replay remain open.
- A cached v4.1 reply now retains the effective RPC credentials from its
  original request. A changed-UID `AUTH_SYS` retry of the same slot/sequence
  receives `NFS4ERR_SEQ_FALSE_RETRY` without replacing the cache or executing
  a second `REMOVE`; the original user can still replay its cached body with
  a changed AUTH_SYS machine name and target, then advance the slot. This
  checks replay-user consistency, not cryptographic authentication of
  `AUTH_SYS` or recovery of all cache-required oversized replies.
- The server now retains a complete reply whenever it fits the negotiated
  reply-cache bound, even if `SEQUENCE.cachethis` is false. A real-TCP test
  removes one file with that hint unset, retries the same slot/sequence with
  a different target, and receives the original reply without deleting the
  second file; a fresh sequence then removes it. This is same-process,
  bounded-reply replay, not crash-durable or general cache-required
  oversized-reply recovery.
- When `SEQUENCE.cachethis` is false and the completed reply is too large
  for the negotiated cache bound, the server now caches a compact retry
  marker: the original successful `SEQUENCE` result followed by
  `NFS4ERR_RETRY_UNCACHED_REP` on the original second operation. A real-TCP
  `REMOVE` plus large `READDIR` test proves the marker fits a 128-byte cache,
  repeats byte-for-byte, never re-executes the mutation, and allows the next
  sequence to progress. Cache bounds too small even for the marker remain
  open.
- With `SEQUENCE.cachethis=true`, an oversized read-only `READDIR` result
  after a successful `REMOVE` now becomes a cacheable
  `NFS4ERR_REP_TOO_BIG_TO_CACHE` result when the prefix and error fit the
  negotiated bound. The original mutation's successful result remains in
  the cached reply, and a retry returns that exact reply without repeating
  the mutation. Other variable-size results and prefixes too large even for
  the error reply remain open.
- The same bounded substitution now covers a large `READ` after a successful
  `REMOVE`. A real-TCP 512-byte read under a 256-byte reply-cache bound
  returns `NFS4ERR_REP_TOO_BIG_TO_CACHE` on `READ`, caches the successful
  mutation prefix, replays the exact response without deleting a changed
  target, and permits the next sequence to progress. Other oversized result
  classes and prefixes too large for the error still remain open.
- A separate 512-byte symlink target makes `READLINK` exceed a 256-byte
  cache-required reply limit after a successful `REMOVE`. The server now
  retains the mutation prefix and substitutes the bounded
  `NFS4ERR_REP_TOO_BIG_TO_CACHE` on `READLINK`. A changed-target retry
  returns the cached response byte-for-byte without another deletion;
  the next sequence progresses. This remains same-process evidence.
- A broad `GETATTR` request after a successful `REMOVE` exceeds a 160-byte
  cache-required reply limit. The read-only tail now returns bounded
  `NFS4ERR_REP_TOO_BIG_TO_CACHE` while retaining the successful mutation
  prefix. A changed-target retry returns the same cached bytes without
  another deletion, and a fresh sequence progresses.
- Even fixed-size `GETFH` can overflow a small required reply cache after a
  successful `REMOVE`. The root-handle result makes the reply exceed a
  112-byte bound; substituting `NFS4ERR_REP_TOO_BIG_TO_CACHE` on `GETFH`
  retains the successful mutation prefix and produces an identical cached
  reply on a changed-target retry, without deleting that target.
- When a completed mutating COMPOUND has no reply or retry marker that fits
  the negotiated cache, its session is now fenced. A real-TCP `REMOVE`
  exceeds a 96-byte cache; a changed-target retry receives
  `NFS4ERR_BADSESSION` instead of the prior `NFS4ERR_SEQ_MISORDERED`, and
  cannot delete the other file. Read-only overflow does not trigger this
  fence; the existing state-limit wire case still advances its slot.

  `native-nfs (macos-latest)` and `native-nfs (ubuntu-latest)` successfully:
  macOS covered native NFSv3, CLI persistence/cleanup, and SQLite hosting;
  Ubuntu covered the privileged NFSv3/NFSv4.1 lane and SQLite hosting.
- Qualify cross-process crash, concurrency, and durability behavior; bounded
  cancellation/close now has a local transport lifecycle gate, and the
  host-backed NFSv3 data path now has a forced-process-restart gate. NFSv4
  `FILE_SYNC4` data now has a forced-process-restart readback gate through a
  fresh session; durable lease/replay/file-handle recovery, cross-process
  concurrency, and power-loss durability remain outside the supported local
  claim. The restart gates
  explicitly reject a pre-crash NFSv3 file handle with `NFS3ERR_STALE` before
  recovering the same bytes through a replacement-server LOOKUP, and reject a
  pre-crash NFSv4.1 session with `NFS4ERR_BADSESSION` before dispatch and the
  pre-crash root handle with `NFS4ERR_STALE`.
  The v4.1 forced-crash lane also removes a seeded host file through wire
  `REMOVE`; a replacement-session wire `LOOKUP` returns `NFS4ERR_NOENT` and
  the host path remains absent. This is process-crash namespace evidence,
  not directory-fsync or power-loss durability.
  A separate successful wire `RENAME` of a seeded host file also survives the
