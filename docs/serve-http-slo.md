# serve-http service levels and backup

What an operator of `mount-rs serve-http` can measure today, starting
objectives to adapt, the latencies the project has measured, what cannot be
measured yet, and what is and is not qualified for backup.

Nothing in this document is a guarantee. The project publishes no
service-level agreement. Objectives are the operator's to set.

Related documents:

- Operator runbook (health, observability, alerts, backup): [`serve-http-runbook.md`](serve-http-runbook.md)
- Compatibility policy: [`serve-http-compatibility.md`](serve-http-compatibility.md)
- Upgrade and rollback: [`serve-http-upgrade.md`](serve-http-upgrade.md)
- Security: [`serve-http-security.md`](serve-http-security.md)
- API guide: [`transports/mount-rs-http/README.md`](../transports/mount-rs-http/README.md)

## Where measurements come from

The server exposes no metrics endpoint. It adds a request id to every
response, and with `"access_log": true` writes one line per request to
stderr (status, duration, route template, byte counts, request id), which is
off by default. The runbook's "Observability" section describes both and
keeps the reverse proxy as the source of request metrics. Every indicator below is therefore measured at one of
three places:

| Source | Gives |
| --- | --- |
| The reverse proxy or load balancer | Per-request status, method, path, upstream response time, bytes |
| A probe (load balancer health check or blackbox prober) | `/healthz` and `/readyz` status over time; a synthetic read-after-write |
| The service manager and process stderr | Exits, restarts, `http_accept_failed` lines, `mount_cache_stats` lines if enabled |

## Service-level indicators

### Availability

| Indicator | Definition | Source |
| --- | --- | --- |
| Request availability | Good requests / valid requests, per drive, over the window | Proxy access log |
| Readiness | Fraction of probes in which `GET /readyz` returned `200` | Probe |
| Synthetic read-after-write | Fraction of probe runs in which a `PUT`, a `GET` of the same path returning the same bytes, and a `DELETE` all succeeded | Prober with its own token on each drive |

Classifying a request from the proxy log:

| Status seen by the client | Counts as | Reason |
| --- | --- | --- |
| `2xx`, `304`, `206` | Good | |
| `400`, `401`, `403`, `404`, `405`, `406`, `409`, `412`, `413`, `414`, `416`, `501` | Good (the service answered correctly) | The contract defines these as caller-correctable. Track `401` and `413` separately as signals, as the runbook's alert table does. |
| `500`, `504` | Bad | Storage or server failure; request timeout |
| `503` | Bad | A drive failed closed (`ESTALE`), contention (`EAGAIN`/`EBUSY`), or shutdown |
| `507` | Bad | Storage full. Operator-correctable, so it is the service's failure, not the caller's |
| `502` and other errors generated by the proxy | Bad | Process down, connection limit reached, or a keep-alive race |
| Connection failure before any status | Bad, but **not visible in the proxy log** if the client never reached the proxy | Measure with the prober |

Notes:

- Exclude `/healthz` and `/readyz` from request availability; they are
  probes.
- The proxy log has the drive id in the path (`/v1/drives/<id>/...`), so
  availability can be split per drive. The server gives no per-drive figure.
- `/readyz` has limits the runbook states plainly: the probe does no I/O;
  a split-store failure is noticed only after an operation or the
  background lease renewal records it; the storage of a `host` or `sqlite`
  drive is checked every two seconds for being there, not for being
  writable. Readiness is a lower bound on trouble, not a measure of health.
  Use the synthetic read-after-write to cover what it does not.
- A `400 EIO` (the client aborted its upload) is the caller's doing and is
  counted as good.

### Latency

| Indicator | Definition | Source |
| --- | --- | --- |
| Metadata read latency | Upstream response time of `GET`/`HEAD` on `/stat`, `/lstat`, `/statfs`, `/readlink`, `/entries`, and `HEAD` on `/fs` | Proxy (`$upstream_response_time` in nginx, or your proxy's equivalent upstream timer) |
| Metadata mutation latency | Upstream response time of `POST /ops/mkdir`, `/ops/rename`, `/ops/truncate`, `/ops/sync` and `DELETE /fs` | Proxy |
| Download time to first byte | Upstream header time of `GET /fs` | Proxy (`$upstream_header_time`) |
| Transfer rate | Bytes / upstream time for `PUT /fs` and `GET /fs` above a size threshold | Proxy |

Notes:

- Do not put file transfers in a latency percentile with metadata calls.
  Their duration is proportional to size, and a streamed upload has no
  overall time limit.
- Listing latency grows with directory size (up to 100,000 entries by
  default). Either track `/entries` separately or accept a wider objective
  for it.
- Measure at the proxy's upstream timer, not the client-facing timer, to
  exclude slow clients. Add a client-side or prober measurement for the
  end-to-end figure including TLS.
- No request can exceed `request_timeout_ms` (30 s) before its response
  headers, except a streamed upload: the server answers `504` itself. The
  latency distribution of non-streamed requests is therefore capped at that
  value, and the `504` count is the tail.

### Correctness and durability

There is no indicator the server exposes for these. The contract's promises
(atomic `PUT`, durable before `200`) are established by the contract tests
and the end-to-end probe in CI, not by a runtime signal. An operator can
measure only the synthetic read-after-write above, and a periodic restore
rehearsal.

## Suggested starting objectives

**These are suggestions to start from, not project commitments and not
measured results.** They are chosen from the mechanics below. Replace them
with figures from your own baseline after two to four weeks of data.

| Objective | Suggested start | Basis |
| --- | --- | --- |
| Request availability, per drive, 30 days | 99.9% | See the downtime arithmetic below. A single-process service with restart-only upgrades and a lease wait after a crash cannot honestly promise more. |
| Readiness probes returning `200`, 30 days | 99.9% | Same. |
| Synthetic read-after-write success, 30 days | 99.9% | Same. |
| Metadata read latency at the proxy, p99 | 50 ms | Two orders of magnitude above the loopback reference figures below, to leave room for the proxy, the network to remote storage, and noisy hosts. Tighten once measured. |
| Metadata mutation latency at the proxy, p99 | 500 ms | The reference run's durable TiDB mutations have a p99 between 9 and 330 ms on a shared runner, depending on the operation and route. SQLite-backed mutation latency was not measured by that run. |
| Download time to first byte, p99 | 250 ms | Not measured by the project. A placeholder. |
| `504` responses | Fewer than 0.1% of requests | A `504` is a request that hit `request_timeout_ms`. |

### Downtime arithmetic

The availability objective is bounded by facts in the runbook:

- **Almost every change is a restart.** Binary upgrades, config changes
  and cold backups each stop the service, and so does rotating a token that
  comes from an environment variable. The one change that does not is
  rotating a token that comes from a file (`token.file`), which is reloaded
  while the server runs. There is no second instance of a drive.
- **A clean restart** costs the drain of in-flight requests (up to
  `drain_timeout_ms`, 35 s by default, plus up to 5 s), the storage flush,
  and the start. The project has not published a measured figure for this;
  measure your own.
- **An unclean stop** (SIGKILL, crash, host loss) costs, in addition, up to
  one lease lifetime before a new process can open a split-store drive: 240 s
  by default for a structured `storage` object.
- **A drive that fails closed does not recover by itself.** It returns
  `503` until the process is restarted, so time to detect and restart counts
  in full.

| Monthly objective | Error budget (30 days) | What fits |
| --- | --- | --- |
| 99% | 7 h 12 min | Comfortable for a single node with manual response |
| 99.9% | 43 min | About ten unclean recoveries at the default lease, or dozens of clean restarts, with automated restart |
| 99.95% | 21.6 min | About five unclean recoveries; needs prompt automated detection of `/readyz` 503 |
| 99.99% | 4.3 min | **Not achievable with the default lease if there is one unclean stop in the month**: a single 240 s lease wait consumes the budget. Would need a shorter `lease_ttl_ms`, which the runbook warns leaves less headroom for slow storage. |

Scheduled maintenance can be excluded from the objective by agreement with
consumers. Say so explicitly if you do; the API guide tells consumers only to
retry `503` and connection failures with back-off.

## Measured reference latencies

These are the project's own measurements. They are **not a production
guarantee** and are not an objective.

### Conditions

| | |
| --- | --- |
| Source | [`apps/site/src/content/benchmarks.ts`](../apps/site/src/content/benchmarks.ts), produced by the "Metadata latency" workflow (`.github/workflows/metadata-latency.yml`, `scripts/metadata-latency-bench.py`) |
| Run | [`44015339854`](https://github.com/andymac4182/mount-rs/actions/runs/44015339854), 17 November 2026 |
| Machine | One GitHub-hosted `ubuntu-latest` runner: 4 vCPU Intel Xeon 6973P-C, 15 GiB |
| Topology | Three `serve-http` processes on loopback forming a forwarding cluster, 100 drives spread across them, plus TiDB (one TiKV), RustFS and Redis in containers on the same runner |
| Load | One client per drive, each on its own keep-alive HTTP/1.1 connection, 10 requests a second per client, 20 measured seconds per mode |
| Path | Client to server directly over loopback, cleartext. **No TLS, no reverse proxy, no network.** |
| Operations | `ping` is `GET /readyz`; `stat` is `GET /stat/<file>`; `head` is `HEAD /fs/<file>`; `list` is `GET /entries/<dir>` on a 20-entry directory; `mkdir`, `rename` and `delete` are the corresponding mutations |
| Routes | "Local": the client calls the server that owns its drive. "Forwarded": the client calls another server, which forwards to the owner over HTTP/3 |

How this differs from a v1 deployment:

- The servers ran with `forwarding` configured, which is the experimental
  cluster configuration, not the plain v1 one. The "local" rows are the
  closest to a single-node v1 server. The "forwarded" rows describe a feature
  outside v1.
- Everything shared one 4-vCPU machine, so the servers competed with the
  databases and the load client for CPU.
- There was no proxy. A production request adds TLS termination and a proxy
  hop.
- File reads and writes (`GET` and `PUT` of content) were not measured.
- In SQLite mode only `ping` and `stat` were measured. **There is no
  measured mutation or listing latency for SQLite-backed drives in this
  run.**

Reading these:

- Reads take a fraction of a millisecond in every mode on the local route.
  That is close to the server's own overhead on loopback.
- In durable TiDB mode a mutation is committed to TiDB before the response.
  Its latency is TiDB's commit latency on that runner, and the tail (p99 of
  tens to hundreds of milliseconds) reflects a single TiKV sharing four
  vCPUs.
- "Writeback (exclusive)" acknowledges mutations from memory and publishes
  them afterwards. It is fast because it gives up "durable before `200`".
  `production-readiness.md` records that creates and renames made in this
  mode without a sync are lost on SIGKILL or power loss. Do not read these
  rows as the latency of durable writes.
- With 2,800 to 10,000 samples per row, a p99.9 rests on three to ten
  samples. Treat that column as indicative.

### Other measurements in the runbook

The runbook's "Capacity" section records, from one Mac and a SQLite

## What cannot be measured from the server yet

All of the following are stated as absent in the runbook's "Observability"
table, or follow from it.

| Wanted | Status in the default build | Workaround |
| --- | --- | --- |
| Request count, status and latency from the server itself | **Partly.** Per request, with `"access_log": true`: an `http_request` JSON line on stderr with status and duration. No metrics endpoint and no aggregation | Derive counts and latencies from those lines in the log pipeline, or use the proxy's access log and metrics |
| Why a request got a `500` | **Not implemented.** The client receives a POSIX code; the underlying storage message is not logged anywhere | Correlate by time with storage-side logs |
| Request ids in responses | Implemented: every response carries `X-Request-Id`, echoed from the request when it is safe | Have the proxy pass or set `X-Request-Id` and log it |
| Trace headers in responses | **Not implemented** | |
| Time spent in storage per request | **Not implemented** | Storage-side metrics |
| Lease renewal latency or margin before a drive fails closed | **Not implemented.** The only signal is `/readyz` turning `503` after the fact | Monitor the metadata store's latency directly |
| Health of `sqlite`-kind, `host` and `memory` drives | **Not implemented.** They never report unhealthy | Synthetic read-after-write |
| Current connection count against `max_connections` | **Not implemented** | Count upstream connections at the proxy or on the host |
| Upload memory budget in use; requests waiting for it | **Not implemented.** Saturation shows only as `504` on uploads | Watch upload `504`s and upload concurrency at the proxy |
| Per-drive figures | **Not implemented** in the server | Split the proxy log by the drive id in the path |
| Cache hit rates | Available: `mount_cache_stats` lines on stderr with `cache_report_interval_seconds`, for drives with a cache | |
| Failed `accept` calls | Available: `http_accept_failed` lines on stderr | |

With the CLI built with `--features observability` and run with
`MOUNT_RS_TELEMETRY=1`, the server records a span, a completion event and the
`mount_rs.operations`, `mount_rs.errors` and `mount_rs.operation.duration_ms`
metrics per request. **The CLI installs no exporter**, so in a stock
deployment these go nowhere; only an embedding application that supplies a
subscriber and exporter receives them. See [`observability.md`](observability.md).

### Where the gap is tracked

- The runbook's ["Observability"](serve-http-runbook.md#observability)
  section is the authoritative statement of what exists.
- [`production-readiness.md`](production-readiness.md), "Gaps found outside
  the audit", lists statement timeouts missing for PGlite and TiDB (rated
  High): a stalled TiDB hangs a statement and every operation queues behind
  it. On `serve-http` that would be expected to show as request timeouts
  (`504`); this was not tested.
- **There is no GitHub issue for the missing metrics endpoint.** (Request
  ids and an opt-in access log have since been added.) At the time of writing the repository's issue tracker has
  one open issue, on an unrelated subject. The gap is recorded only in the
  two documents above. Opening an issue for it is recommended, so that
  [`maturity.md`](maturity.md)'s requirement for "the observability a
  deployment needs" has something to close against.

## Backup

### What is qualified

**One procedure: a cold copy of a SQLite-backed drive.** The runbook states:
"There is no backup command in `mount-rs` and no qualified online backup
procedure. The supported procedure is a cold copy." That statement was
checked for this document: the CLI has no backup, snapshot or export
subcommand (`apps/mount-rs-cli/src/parser.rs`), and no test or script was
found that copies a drive's storage while the service is running.

The procedure, with its restore steps and notes, is in the runbook under
[Backup and restore (SQLite-backed drives)](serve-http-runbook.md#backup-and-restore-sqlite-backed-drives).
It is not repeated here. In outline: stop the service cleanly, copy the
metadata and block databases together, start the service.

### What is not qualified

| Method | Status |
| --- | --- |
| Copying the SQLite files while the service runs | **Not qualified.** The metadata and block databases are one unit and must be consistent with each other; the runbook says a mismatched pair produces missing-block or hash-mismatch errors. It also notes that a copy taken from a running process carries a live lease, so a start from it first waits for the lease to expire. |
| SQLite's online backup API, `VACUUM INTO`, or `sqlite3 .backup` against a live drive | **Not tested.** Each could give a consistent copy of one database; nothing coordinates the pair. |
| A filesystem or volume snapshot taken while the service runs | **Not tested.** The runbook accepts a snapshot only "while the process is stopped". |
| A backup through the API (listing and downloading every file) | **Not qualified as a backup.** Downloads are not snapshot-isolated, listings fail above the entry limit and a paginated listing is not a snapshot either, and there is no change feed. It yields a file-level copy with no consistent point in time. |
| Drives on TiDB, PGlite, FoundationDB or object stores | **No procedure in this repository for `serve-http`.** The runbook defers to those systems' own tools. The same pairing concern applies in principle: a metadata store restored to a point in time must still find every block it references in the block store. Whether a given provider pair tolerates a metadata restore without a matching block restore was not examined here. |
| Point-in-time recovery, incremental backup, continuous replication to a standby | **Not implemented** in `mount-rs`. |

### Consequences for objectives

- **Recovery point.** Equal to the interval between cold backups. Every write
  acknowledged after the last backup, including a `PUT` that returned `200`,
  is lost on restore.
- **Backup costs availability.** Each cold backup is a clean stop and start.
  A nightly backup is 30 restarts a month against the error budget above,
  unless agreed with consumers as scheduled maintenance.
- **Recovery time.** Time to copy the databases back, plus a start. If the
  restored copy carries a live lease (taken after a crash rather than a clean
  stop), add up to one lease lifetime.
- **Verifying a restore.** After a restore, check `/readyz` and read a known
  file, as the runbook says. For a split-store drive the driver option
  `verify_backing_blocks` checks at startup that every referenced block is
  present and long enough; the CLI README notes it reads the whole referenced
  block set and does not detect same-length corruption.
- **Rehearse.** The runbook's pre-launch checklist requires one rehearsed
  cold backup and restore. Repeat it after any change of storage layout.
