This inventory records the input domain and property of each locally executed proof. A passing bounded proof applies to its stated harness, not to the whole workspace. The full local runner passed all 15 harnesses with Kani 0.68.0 and CBMC 6.11.0 on 64-bit aarch64 macOS; each reported `VERIFICATION:- SUCCESSFUL` in its own invocation.

After installing and setting up Kani, check that `./scripts/cargo-shared kani --version` reports 0.68.0, then run the local proof set from the repository root with:

```sh
./scripts/verify-formal
```

The script invokes the repository-required `./scripts/cargo-shared` wrapper and runs every harness separately so its failed checks and cover properties stay attributable to one proof. FSKit has an independent Cargo workspace, so the script enters `transports/mount-rs-fskit` for its proof. The FoundationDB proof enables the `foundationdb` feature and needs that feature's native build dependencies.

Kani emitted global unsupported-construct warnings for `caller_location (1)` and `foreign function (2)` in the core crate. Their instrumented checks were unreachable in the core extent harnesses. The passing results do not cover code paths using those constructs.

## Publication schema compatibility

Versioned publications now persist caller-supplied namespaces as `NamespacePublication`, reserving `Snapshot` for coordinator live capture. Exact-payload retries of old explicit publications stored as `Snapshot` still reconcile and return their immutable legacy kind; a different payload returns `EEXIST`. An old explicit row cannot be distinguished from a true old snapshot by kind alone, so a reused ID can still be ambiguous for `snapshot_with_publication_id`.

SQLite and PGlite keep the versioning schema at version 1 on ordinary open/reopen and Snapshot-only writes. The transaction that first inserts a `NamespacePublication` also activates schema version 2; the SQLite failure regression verifies that an uncommitted insertion leaves both the row and the version unchanged. A version-1 reader can reopen before that commit and rejects a version-2 store on a new connection afterward. Already connected old readers are not re-gated, so they must be drained before using the new kind. Rollback after activation requires a compatible reader, and downstream exhaustive `VersionKind` matches must add the new variant.
